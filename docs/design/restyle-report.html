Fancy Window Restyle
Design study · Fancy Window 2.x

Fancy Window, restyled like a modern code editor

Five mockups that bring Visual Studio Code's look to Fancy Window, each checked against how the app is really built: Rust, raw Win32 and GDI, one ~2.5 MB exe, no Electron and no WebView. Every idea below can be painted by the code that already draws the menu bar, zones and status bar.

Overview

All five ideas together

One title bar holds the icon, the menus, a command-center box that shows the current workspace, and the caption buttons. A rail on the left opens layouts and workspaces. Each zone gets a header with the hosted window's icon and title. The active window gets a bright accent bevel and glow, and the status bar turns accent blue and carries live state.

Idea 1

One title bar for the menus and caption buttons

VS Code puts its menus, a search box and the window buttons in one 35 px row. Fancy Window spends 57 DIP on a native caption plus its own menu bar. Merging them gives that space back to the zones. The centre box shows the loaded workspace and opens the command palette when clicked.

What it takes in Win32

EffortMedium 2–3 days
Exe size≈ 0 KB
Toucheswindow.rs, view/paint.rs
  • Handle WM_NCCALCSIZE (return 0 when wParam is TRUE) to drop the native caption, and call DwmExtendFrameIntoClientArea with a 1 px top margin so the window keeps its DWM shadow and resize edges.
  • Answer WM_NCHITTEST with HTCAPTION over empty title-bar space and HTMINBUTTON/HTMAXBUTTON/HTCLOSE over the buttons. HTMAXBUTTON is what makes the Windows 11 Snap Layouts flyout appear.
  • Paint the caption glyphs with the Segoe Fluent Icons font (fall back to Segoe MDL2 Assets on Windows 10). draw_menu_bar already lays out and paints the menu titles, so it moves up a row.
  • Risks: a maximised window overhangs the screen by the frame width, so the title row needs extra top padding then. Watch DPI changes between monitors, the inactive-window caption colour, and High Contrast mode.
Idea 2

Zone headers and a clear active window

Each zone gets a 28 px header, like an editor tab, with the hosted app's icon and title, its position in the cycle order and a button that lets the window go. The zone whose window has focus gets a 2 px accent line on its header, a bright 1 px bevel and a soft accent glow. Empty zones say how to fill them.

What it takes in Win32

EffortMedium 2–3 days
Exe size≈ 0 KB
Touchesapp/attach.rs, view/paint.rs, window.rs
  • Active state: an EVENT_SYSTEM_FOREGROUND WinEvent hook sends a new Msg whenever focus changes, and AppState records which hosted window is in front. This is the brighter glow and bevel already in progress. The headers and the glow both read that one field.
  • Header content: GetWindowTextW for the title. For the icon, use WM_GETICON via SendMessageTimeoutW (so a hung app can't stall Fancy Window), fall back to GCLP_HICONSM, and draw it with DrawIconEx. EVENT_OBJECT_NAMECHANGE keeps titles current.
  • Geometry: host_rect gains a top inset equal to the header height. It is pure, unit-tested code, so the change is small and testable.
  • Glow in GDI: GDI has no alpha, so the theme pre-blends colours the way Color::over already does. Draw two or three concentric rounded outlines that fade from the accent toward the zone fill. A truly soft blur would need Direct2D (see the summary table).
  • Risks: some apps (UWP hosts, elevated windows) won't give up their icon or title, so the header falls back to the exe name. Headers take 28 DIP from every zone, so offer "Show zone headers" as a preference.
Idea 3

A command palette for every layout, workspace and command

Ctrl+Win+P (global) or a click on the title-bar box opens a filter list. You type a few letters and press Enter. It reaches all 9 layout presets, the 9 workspace slots, the margin and stay-back commands and zone edits, each with its current hotkey, so nothing needs to be found in a menu.

What it takes in Win32

EffortMedium 2 days
Exe size≈ 5–10 KB
Touchesnew app/palette.rs, platform/palette.rs
  • Most of the data already exists. menu_bar(), PRESETS, workspace_menu() and CONFIGURABLE already describe every action as plain MenuItem data with labels and chords. Flattening that tree gives the palette list for free.
  • The filtering and ranking go in app/ as a pure function, unit-tested like the rest of the model. The platform side is one owned WS_POPUP with an EDIT control, an owner-drawn list painted with the existing gdi helpers, and the existing Dialog message loop for keys.
  • Chosen items go back as Msg::Menu(action), the same way menu picks do now, so no new behaviour paths are needed.
  • Risks: a global Ctrl+Win+P may already be taken. The shortcuts dialog already detects that and lets the user pick another chord.
Idea 4

A status bar that shows what's happening

Today the status bar shows "?" and the version. In VS Code it is the quickest place to read state. Here it would show the workspace (click to switch), how many zones hold windows, the margin (click to step it), and a warning segment while Fancy Window is held at the back.

What it takes in Win32

EffortSmall under a day
Exe size≈ 0 KB
Touchesview/paint.rs, app/state.rs
  • draw_status_bar already paints segments and status_help_rect already hit-tests one. Generalise that into a list of segments, each with a MenuAction, and send clicks through the existing Msg::Menu.
  • Everything shown is already in AppState (attachments, margin, stay_back, profile) except the loaded workspace name. Add one Option<usize> that workspace::load sets and any layout edit clears.

Idea 5

An activity rail with layouts you can see

A 48 px rail on the left opens a side panel. The panel shows the nine preset layouts as thumbnails and the workspace slots with their hotkeys. Clicking a thumbnail applies it, carrying windows over in reading order as the Layout menu does now. The panel closes with the rail button or Ctrl+B, so the zones get the full width back.

What it takes in Win32

EffortMedium 2–3 days
Exe size≈ 0 KB
Touchesview/mod.rs, view/paint.rs, app/state.rs
  • The thumbnails cost nothing extra: GridLayout::zone_rects already computes zone rectangles for any canvas size, so each preset is drawn by asking for a 72×45 canvas.
  • canvas_size and Frame gain a left offset (rail width, plus the panel when open). update() already reflows hosted windows whenever the frame changes, so opening the panel moves them automatically.
  • Icons are glyphs from Segoe Fluent Icons drawn with DrawTextW, so there are no image assets and no size cost.
  • Risks: this changes how much room a fresh window gives its zones. Keep the panel closed by default and remember its state in settings.json. Of the five ideas, the rail is the one users could do without most easily.

Recommendation

Suggested build order

Small, self-contained wins come first. Each step leaves the app shippable and keeps the Model-View-Update split intact: new state and logic go in app/ with tests, and pixels go in view/.

  1. Active-zone glow and bevel, plus the typography swap. The glow is already being built. The font change is one line with a fallback. Together they make the app look current with almost no risk.
  2. Live status bar. Under a day, and it answers "which workspace am I in?" and "is it held at the back?" at a glance.
  3. Zone headers. The biggest usability gain: you can tell what's in each zone without hunting for it, and you can release a window with one click. Ship it behind a preference.
  4. Unified title bar. This is the change that makes it look like VS Code, and it returns about 26 DIP of height. Test it on a maximised window, across mixed-DPI monitors, and with Snap Layouts.
  5. Command palette. Most of the plumbing exists already. Do it once the title-bar box is there to open it.
  6. Later, or never: the activity rail (nice, but it takes width), owner-drawn menus, and Mica. Mica only makes sense together with a Direct2D renderer.
